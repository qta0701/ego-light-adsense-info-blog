## 1. 실행 범위와 계정 배정

| ego 프로필 이름 | 네이버 ID | 현황 시트 계정 열 |
|---|---|---|
| 박상민 | chocolateelf | L: 4.chocolateelf |
| 상민-서브계정2 | almawade1 | I: 1.almawade1 |
| 상민-투넘버 | qta14 | J: 2.qta14 |
| 순분 | supportimes001 | K: 3.supportimes001 |

1. 조정자가 2절의 시트 팝업 또는 사용자 지정 목록에서 전체 후보를 확보하고 실제 행·원고·현황 시트·로컬 상태를 대조한다. 동일 탭·실제 행 또는 동일 탭·키워드가 겹치면 하나의 작업으로 확정할 수 있는지 확인한다. 기존 공개·예약이 확인된 글은 필요한 시트 복구로 넘기고 신규 후보는 계정을 배정한 뒤 편집 전에 해당 블로그의 공개 글과도 대조한다.
2. 네 프로필 순서를 한 번 무작위로 섞고 라운드로빈 배정한다. 4개 이하는 서로 다른 프로필, 6개는 2/2/1/1처럼 계정별 수 차이가 최대 1이 된다. 하나의 키워드를 여러 계정에 중복 게시하지 않는다.
3. 배정 결과와 `indexOnProfile`을 파일에 저장한다. 재시도마다 다시 추첨하지 않는다. `indexOnProfile`은 같은 계정의 **예정 시각 배정 순서**이며 실제 제출·완료 순서나 대기 조건이 아니다. 같은 계정의 서로 다른 행도 별도 Space에서 작성·검수·발행 설정·최종 제출·결과 확인을 각각 독립적으로 병렬 진행한다.
4. `ego-browser skill`을 끝 표시까지 읽는다. `profiles()`에서 사용자가 지정한 **이름**으로 실제 ID를 찾는다. 최초 실측 ID는 박상민=Profile 1, 순분=Profile 2, 상민-투넘버=Profile 3, 상민-서브계정2=Profile 4였으나 하드코딩하지 않는다.
5. 선택한 프로필로 TaskSpace를 만들고 네이버 화면에 표시되는 로그인 ID를 대조한다. 닉네임이나 프로필 이름만으로 계정 일치를 판단하지 않는다. 로그아웃·다른 계정·추가 인증이면 같은 Space에서 로그인/사용자 인증 절차를 따른다. 비밀번호·쿠키를 파일이나 출력에 저장하지 않는다.
6. 해당 Space가 네이버 블로그 작업과 무관한 페이지에 있으면 같은 Space에서 `https://www.naver.com/` 또는 배정된 네이버 ID의 `https://blog.naver.com/{네이버ID}`로 돌아가 로그인 ID와 블로그 주소를 확인하고 작업을 이어간다. 네이버 ID는 배정표의 실제 계정으로 넣는다. 기존 편집창에 저장되지 않은 내용이 있으면 이동 전에 보존하고, 필요한 경우 같은 Space의 다른 페이지를 사용한다. 로그인·추가 인증 또는 사용자 제어 상태를 우회하기 위해 새 Space나 다른 도구를 사용하지 않는다.

### 섹션별 독립 채팅과 키워드별 Space

- 사용자가 섹션별 독립 채팅을 요청하면 조정자가 **섹션 수만큼 실제 Codex 새 채팅**을 만들고 각 섹션을 하나씩 배정한다. 하위 에이전트나 브라우저 탭을 새 채팅으로 보고하지 않는다. 이 저장소의 요청 프롬프트에는 새 채팅과 복수 Space 사용 요청이 명시되어 있다. 현재 요청이 이 문서를 참고만 하고 새 채팅을 요청하지 않았다면 채팅을 임의로 만들지 않는다.
- 각 섹션 채팅은 키워드마다 지정 프로필의 별도 ego TaskSpace를 하나씩 만들고, 배정된 행 중 최대 3개 Space를 동시에 진행한다. 이 3개는 채팅별 한도이며 모든 채팅을 합친 전역 한도가 아니다. 예를 들어 4개 채팅에 각각 3개 키워드가 준비되면 총 12개 Space를 목표로 한다. 실제 브라우저·계정의 전역 슬롯과 시스템 자원을 확인하고, 12개가 보장되거나 지침 변경만으로 슬롯이 늘어난다고 가정하지 않는다. 같은 프로필·네이버 ID에 배정된 다른 키워드가 여러 섹션에 있어도 발행 제출과 결과 확인까지 병렬로 진행한다. 인증·시트 확인 대기 중인 Space도 실제 슬롯에 포함한다. 한도에 도달하면 제약을 기록하고 가능한 행부터 진행하며, 대기 행은 슬롯이 비는 즉시 시작한다.
- 사용자가 Space를 미리 만들 필요는 없다. 각 작업자가 설치된 `ego-browser skill`을 끝까지 읽고 `profiles()`로 실제 이름과 ID를 확인한 뒤 배정 프로필로 Space를 생성한다. `profileId`는 생성 시 적용되므로 기존 Space의 프로필을 바꿀 수 있다고 가정하지 않는다. 사용자 소유 Space를 임의로 claim하지 않으며, 인증·사용자 제어·오류 복구를 위해 새 Space로 우회하지 않는다.
- 조정자는 전체 키워드의 **하나의 균등 배정표와 계정별 예정 시각표**를 저장하고 각 채팅에 전달한다. 각 행·키워드는 하나의 작업자와 로컬 claim에만 배정한다. 계정별 최신 공개 글을 한 번 확인해 각 행에 시각을 배정한 후, 각 행은 자체 계정 확인과 검수를 마치는 즉시 배정된 즉시/예약 설정으로 제출한다. 다른 행이나 Space의 작성·실제 발행·제출 결과, 계정 내 앞선 행의 확정, 조정자의 추가 제출 허가를 기다리지 않는다. 어떤 행의 제출 결과가 불확실해도 다른 행은 진행한다. 불확실한 **그 행 자체**는 결과를 확인하기 전 중복 제출하지 않는다.
- 인계 정보: runId, 섹션, 탭/실제 행/키워드/URL, 상대 폴더, 프로필 이름/계정, Space ID, 현재 단계, 작업자가 이미 소유한 동일 글의 체크포인트 또는 공개 URL, 금지할 중복 작업. 같은 키워드를 재시도할 때는 저장된 배정·claim·Space와 해당 글의 작업 상태를 대조한다. 계정 내 다른 행의 결과는 선행 조건이 아니다.
- 사용자에게 진행·로그인·오류·재개 위치를 알릴 때는 Space 이름 대신 **시트 탭·실제 행 번호와 ego-browser Space 번호**를 함께 표기한다. 예: `앱사용 41행 · Space 9`. 필요한 경우 배정 네이버 ID도 덧붙인다.
- 조정자 한 명이 시트 조회·쓰기와 현황 행 확정을 담당하고, 작업자는 각 글의 발행 근거와 결과를 반환한다. 채팅 생성이나 동시 실행을 지원하지 않는 환경에서는 이를 실제로 수행한 것처럼 기록하지 말고 제약과 가능한 재개 방법을 보고한다.
- 네이티브 클립보드·이미지 선택·캡처 등 공유 자원은 충돌하지 않도록 모든 참여 채팅이 같은 프로젝트의 `tools/naver_editor.mjs` `withEditorLease`로 해당 짧은 편집 배치를 직렬화한다. 다른 도구·프로젝트가 같은 잠금을 쓰지 않으면 별도 공용 조정이나 시간 분리가 필요하며, `capture()`의 프로세스 내부 큐만으로 전역 직렬화된다고 가정하지 않는다. lease가 사용 중이면 현재 단계를 보존해 기다린 뒤 획득을 재시도한다. 다른 실행의 lock을 자동 삭제하거나 실패한 입력을 통째로 재실행하지 않는다. 나머지 독립 작업은 병렬로 진행한다.

## 2. 시트와 원고 사전 확인

콘텐츠표는 [1.애드센스 키워드표](https://docs.google.com/spreadsheets/d/1KAnq9pvZ7VYFJOAQ_25cM8EjaDFUX5Z6x9jfCCtTf7s/edit?usp=sharing)다. 제목이 바뀌어도 URL의 문서 ID로 확인한다.

### 2.1 시트 스크립트 메뉴에서 네이버 포스팅 미진행 후보 가져오기

1. 설치된 `ego-browser skill`을 끝까지 읽고 공개 SDK로 조회용 TaskSpace에서 콘텐츠표를 연다. 메뉴가 좁은 창에 가려지면 [웹자료수집.md 8.1절](웹자료수집.md#81-팝업-조회-및-목록-저장)의 `ensureSheetsMenuWidth(page)`로 2,150px 너비를 요청한다. 실제 창과 뷰포트 적용 방식을 확인하고, 에뮬레이션이면 메뉴를 조작할 SDK 라운드마다 재호출한 뒤 새 snapshot을 사용한다.
2. 상단 `🔍 키워드 조회` → `1️⃣1️⃣ 네이버 포스팅 미진행 전체 시트 조회 (팝업)`을 실행한다. 스크립트가 완료되고 `전체 시트 네이버 포스팅 미진행 목록` HTML 팝업이 열릴 때까지 기다린다. 결과 0건, 스크립트 오류, 로그인·권한 요구를 구분한다. 사용자 조작이 필요하면 같은 Space에서 제어를 넘겨 확인 후 재개한다.
3. 기본은 `📋 전체 기본 복사`로 전체 목록을 확보한다. 연속 목록은 `📑 연달아 모두 복사`, 분할 목록은 대상 탭의 분할 크기를 정한 뒤 `📑 연달아 분리된 섹션 전체 복사`를 사용한다. 버튼이 탭별로 제공되면 대상 탭마다 복사해 탭 이름을 함께 기록한다. 복사한 텍스트를 확인하고, 중첩 iframe의 버튼 조작이 실패하거나 복사 결과를 읽을 수 없으면 팝업 snapshot 또는 iframe subtree에 표시된 요약과 섹션 텍스트박스를 읽는다. 복사 확인에는 팝업과 복사 결과만 사용한다.
4. 목록을 `{tab, row, keyword}`로 정리한다. `row`는 `No.`와 구별되는 **실제 시트 행 번호**다. 팝업의 탭·행 순서와 표시된 분할 경계를 유지한다. 분할 경계가 없으면 탭별 목록을 각각 한 섹션으로 사용한다. 전체 행·탭 수와 섹션별 건수를 대조하고, 같은 탭·행 중복, 키워드 충돌, 탭 누락 또는 건수 불일치는 원래 목록에서 재확인한다. 탭이 다르면 같은 행 번호도 별개다. 기본 범위는 팝업 전체이며, 범위가 별도 지정되면 팝업 순서로 해당 범위를 적용한다. 0건이면 조회용 Space를 정리하고 조회 결과를 보고한다.
5. 조회 시각, 팝업 순서·섹션, 탭·실제 행·키워드를 실행 기록에 저장한 뒤 정상적으로 목록 확보를 마친 조회용 Space를 정리한다. 조정자는 2.2절에서 확인한 `spreadsheetId`·`sheetId`, 시트 값, 원고 상대 경로와 삽입 URL의 근거, 배정·복구·보류 사유를 같은 기록에 추가한다. 팝업 조회와 시트 대조는 읽기 작업이다. 재개 요청은 기존 실행의 배정표와 `naver-state.json`의 해당 글·Space를 기준으로 이어간다. 새로 조회된 행은 새 실행에 사용한다.

### 2.2 실제 행, 로컬 원고, 삽입 URL 확인

1. 팝업 조회형과 직접 지정형 모두 연결된 Sheets 도구로 문서 metadata, 정확한 탭의 `sheetId`·헤더·후보 행 CellData를 좁은 범위로 읽는다. `블로그 업로드 날짜`, `네이버 포스팅 여부`, `애드센스 포스팅 링크`, `메인 키워드`를 헤더로 찾는다(현재 A·F·H·I). 목록의 탭·실제 행·키워드를 현재 시트와 대조한다. 행 이동이나 키워드 불일치가 있으면 다시 조회하고, 대응이 확정되지 않는 행은 사유와 재개 지점을 남겨 보류한다.
2. A 날짜를 `YY_MMDD`로 바꿔 `YY_MMDD/{탭}_{키워드}/웹조사/publish/`를 먼저 확인한다. 폴더명에는 `tools/research_pipeline.py`의 기존 이름 정규화 규칙을 적용하고 시트 대조에는 원래 탭·키워드를 사용한다. A가 비었거나 해석할 수 없거나 예상 폴더가 없거나 메타데이터가 다른 행을 가리키면 프로젝트의 `YY_MMDD` 폴더에서 같은 키워드 폴더명을 제한 탐색한다. `웹조사/research.json`, 조사 manifest, 기존 배정 기록 또는 `웹조사/evidence/naver-state.json`에서 탭·행·키워드·경로를 대조한다. 구형 폴더는 폴더명과 조사 문서의 주제를 확인한다. 다른 PC의 절대 경로는 `.antigravity/rules.md`의 경로 해석 규칙을 적용한다. 근거가 일치하는 유일한 폴더를 사용하고, 대응을 확정할 수 없는 행은 보류한 뒤 확인된 행을 계속 처리한다.
3. 필수 원고는 `publish/{탭}_{키워드}_네이버블로그.md`이며 파일명 접두어는 확정한 키워드 폴더명이다. 선택 메타는 `publish/{탭}_{키워드}_네이버블로그_제목 및 이미지 배치.txt`이고, 없으면 기존 `_네이버블로그_제목해시태그.txt`를 참고한다. 둘 다 없으면 키워드가 포함된 제목과 원고에 맞는 이미지 위치를 정한다. 빈 원고·누락 파일은 해당 경로와 재개 지점을 기록한다.
4. 팝업 조회형의 삽입 URL은 같은 행 H의 실제 링크를 읽고, 기존 MD의 CTA 바로 다음 URL과 대조한다. H가 비어 있으면 대응이 확인된 MD의 CTA에서 하나로 일치하는 HTTP(S) URL을 사용하고 출처를 기록한다. H와 CTA가 다르면 시트 행과 원고를 다시 확인한다. 불일치가 남거나 삽입 URL을 확정할 수 없으면 해당 행을 보류하고 차이를 기록한다. 직접 지정형에서 사용자가 URL을 지정했다면 그 값을 우선하고 H와의 차이를 기록하며 사용자가 지정한 범위에 적용한다. 확정한 삽입 URL은 작업 기록의 `promotionUrl`과 7절 현황 시트 F에 사용한다.
5. 원고/TXT의 채택 이미지 순서를 읽는다. `publish/`에 없으면 **동일 키워드의 상위 `웹조사/`에서 정확한 파일명**을 찾는다. 채택한 원본 또는 `_가이드.png`의 파일명을 그대로 확인한다. 채택 이미지를 확보할 수 없는 행은 경로와 재개 지점을 남긴다.
   - 직접 캡처한 화면과 가림·자르기·표식 편집본을 다른 채택 이미지와 같은 방식으로 확인하고 원고의 위치·순서·캡션에 맞춰 업로드한다. 재사용 또는 편집 허용 근거가 확인되지 않았다는 이유만으로 자동 제외하거나 슬롯을 삭제하지 않는다. 실제 파일·화면 내용·개인정보 가림·가독성과 원고의 일치를 확인한다.
   - 게시할 본문과 캡션, 제목·이미지 배치 TXT와 새로 가공하는 이미지에는 이미지 이용 제한에 관한 문구를 추가하지 않는다. 출처와 확인일, 과거 화면이라는 사실 등 독자의 이해에 필요한 정보는 유지한다.
6. 원본 MD/TXT/이미지는 보존한다. 해시·프로젝트 상대 경로·선택 제목·캡션·배정표를 로컬 상태에 기록한다. 게시할 이미지 설명은 글 안의 실제 삽입 순서대로 `1.원래 설명`, `2.원래 설명`처럼 번호를 붙인다. 기존에 같은 형식의 순번이 있으면 중복하지 않고 실제 순서와 맞지 않을 때만 순번을 바로잡는다. 설명 문구와 출처·확인일 등은 유지하고, 설명이 없으면 실제 이미지 내용에 맞는 설명을 정한다. 원본을 수정하지 말고 실행용 복사 계획의 이미지 캡션과 해당 이미지 chunk 캡션을 동일한 번호 문구로 맞춰 입력·검수한다.
7. 채택 이미지 중 글의 핵심 내용을 가장 잘 보여주고 작은 썸네일에서도 알아볼 수 있는 이미지 한 장을 대표 이미지로 선택한다. 주제 적합성·가독성·개인정보 가림과 실제 화면 내용을 확인한다. 첫 이미지라는 이유만으로 고정하지 않는다. 선택한 파일과 순서, 이유를 실행 기록에 남긴다.

### 중복과 잠금

- F, 동일 키워드의 현황 기록, `웹조사/evidence/naver-state.json`과 기존 공개 글을 대조한다. 팝업 후보의 신규 발행에는 F 실제 공란과 중복 확인을 모두 적용한다. F=`ㅇ`이거나 동일 글의 공개·예약 근거가 있으면 실제 결과를 확인해 필요한 시트 기록만 복구한다. F에 다른 값이나 수식이 있거나 기존 글의 결과를 확정할 수 없으면 값을 보존하고 해당 행을 보류한다. 복구 안내가 없다면 다른 임시저장 글의 유무는 발행을 기다릴 조건이 아니다. 동일 글의 체크포인트로 재개할 때는 해당 글을 보존하고 중복 입력·재제출을 피한다. 다른 초안의 내용은 덮어쓰거나 삭제하지 않는다.
- 현황 시트 E열은 metadata의 행 수 안에서 제한 조회하여 동일 키워드와 마지막 데이터를 찾는다. 같은 키워드가 있어도 실제 URL·계정·발행일을 대조한다.
- 블로그 자체 검색은 실제 검색 form action과 `blogId`, `SearchText`를 확인해서 사용한다. 단순 관련 글은 중복으로 오판하지 않는다. 로그인 전용 검색창의 숨겨진 floating input은 피한다.
- 신규 편집 전에 로컬 작업 claim을 확보한다. `tools/blogger_workflow.py`의 `claim/release`를 재사용할 때 `stage: "B"`, 정확한 콘텐츠표 ID/탭/행/상대 폴더, 고유 owner, `platform: "naver"`를 기록한다. 이는 로컬 파일 잠금이며 시트에 임시 표시를 쓰지 않는다. Blogger 결과 상태와 네이버 결과 상태는 분리한다.
- 이미 발행한 글은 재발행하지 않는다. 시트 실패는 동일 공개 URL·원래 발행 시각으로 시트만 복구한다.

## 3. 스타일 변환과 본문 준비

1. 같은 Space에서 `https://blog-editor.supportimes.com/`을 연다.
2. `.md`를 입력하고 `Markdown HTML 변환시작`을 누른다. 원고 변환 결과의 표·소제목·색상·줄바꿈을 확인한다.
3. 이미지 배치 지시만 변환용 **복사본**에서 `NAVERIMG1` 같은 단독 문단으로 바꾼다. **실제 URL은 변환이 끝날 때까지 그대로 둔다.** 변환기는 단일셀 테이블 다음 URL을 보고 CTA를 판정한다. URL을 미리 `NAVEROG1`로 바꾸면 배경이 transparent, 글자가 검정으로 변하는 현상을 재현했다. 원고 자체는 수정하지 않는다.
4. 변환기가 `- 1. 내용`을 `1. 1. 내용`으로 만들 수 있다. 변환 복사본의 `- 숫자. ` 앞 숫자만 제거하거나 출력 검수에서 중복 번호를 고친다. `tools/naver_workflow.py prepare`가 이 작업과 이미지/URL 목록화를 수행한다.
5. 상단 `HTML 복사` 또는 `HTML 저장`을 사용한다. `keyboard.paste({text, html})`로 구조 있는 리치 텍스트를 전달한다. HTML 문자열을 일반 텍스트로 붙이지 않는다.
6. iframe 안의 다운로드 대기가 실패하면 현재 iframe의 실제 `src`를 관찰한다. 이번 실행에서는 동일 변환기인 `https://naver-blog-style-editor-server-745409813694.asia-northeast3.run.app/`을 같은 p2에서 열어 입력/변환/HTML 복사를 수행했다. 주소를 고정값으로 믿지 말고 매번 실제 src를 사용한다.
7. 복사 결과를 로컬에 보존해야 할 때 실제 변환 결과 DOM(`#preview-content`, 이번 실측)을 읽어 HTML 파일로 저장할 수 있다. 페이지 내부의 숨은 앱 상태나 임의 재구현 렌더러로 대체하지 않는다.
8. `convertedChunks`는 실제 변환 결과의 URL 문단을 관찰한 뒤에만 OG 위치 표식을 만든다. CTA td 배경 `#fff8b2`, 텍스트 `#1b1bf8`, 19px, 700을 확인한다. 일반 문장은 계산된 굵기 400을 텍스트 span에도 명시하고, 의도된 소제목·CTA·강조는 유지한다. `<br>`는 네이버에서 별도 p가 되므로 검수 기준 문장도 줄 단위로 나눈다.
9. 조각은 순서·이미지·URL 메타데이터로만 사용한다. `fullRichDocument`로 **본문 전체를 한 번에 리치 붙여넣기**하고, 이후 표식 문단을 이미지/OG로 교체한다. 제목·이미지 캡션 뒤에 본문을 반복 append하는 방식은 기본 경로에서 제외한다.

## 4. 스마트에디터 작성

1. 해당 계정 블로그에서 실제 `글쓰기` 링크를 관찰해 연다. 이번 실측: `https://blog.naver.com/qta14/postwrite`.
2. 편집기 로딩 후 snapshot을 읽는다. 제목은 `.se-title-text p`에서 입력했다. 본문에는 먼저 작은 HTML 조각을 붙여 표가 네이티브 표로 변환되는지 확인한다.
3. 빈 본문에서 굵기 버튼을 해제하고 `fullRichDocument` 전체를 한 번 붙인다. `font-weight:400`만 지정하거나 Ctrl+B만 보내는 방법으로는 기존 굵기 상속을 막지 못한 사례가 있었다. 굵기 버튼 직접 클릭 후 실제 선택 상태 해제를 기다린다. 붙인 직후 일반 문장 전체의 존재와 보통체를 대조한다. `selectMarker`로 유일한 표식 p를 찾아 native triple-click 선택을 확인한 뒤 교체한다. 이미지 표식은 Backspace → 사진 업로드 → 캡션, OG 표식은 plain URL → Enter → 카드 로딩 순서다.
4. **표 선택 상태의 Ctrl+End는 문서 끝을 보장하지 않는다.** 캡션에서 본문으로 이동했다고 추정하지 않는다. 좌표가 필요하면 `behavior:'instant'`로 스크롤하고 현재 p의 사각형을 읽는다. 선택 p의 클래스와 본문/캡션 소속을 확인한다. 빈 본문은 `.se-placeholder` 안내 텍스트를 제외하고 판단한다. 현재 원고의 전체 재구성이 필요하면 본문에서 Ctrl+A → Backspace 후 제목이 유지되고 빈 본문만 남았는지 확인한다. Ctrl+Shift+End가 전체 본문을 선택한다고 가정하지 않는다.
5. paste 후 이미 빈 문단이 생겼으면 Enter를 추가하지 않는다. 텍스트로 끝날 때만 Enter로 다음 삽입 문단을 만든다.
6. `waitForFileChooser()`를 **먼저 등록**하고 관찰된 실제 사진 버튼을 누른다. 이번 실제 버튼은 `button[data-name="image"]`였다. chooser.setFiles(절대 파일 경로)를 호출한다.
7. 이미지 컴포넌트 개수 증가만으로 완료하지 않는다. 전송중 표시가 사라지고 `img.complete && naturalWidth > 0`인지 조건 대기한다.
8. `_hidden-file` 같은 임시 input이 계속 남는다고 가정하지 않는다. 실제 `#hidden-file`은 첫 업로드 후 제거됐다. 반복 업로드는 매번 chooser로 처리한다.
9. 캡션은 **이미지를 먼저 클릭한 뒤** 해당 이미지의 `.se-caption p`를 클릭하여 넣는다. 게시 순서 번호가 붙은 실행용 캡션을 사용하고 `1.원래 설명`처럼 번호·원문 전체를 확인한다. 선택 전에는 캡션 p가 0 크기일 수 있다. 긴 이미지 클릭이 viewport 오류이면 업로드 성공 여부를 먼저 읽고, 이미지의 화면 안 영역 클릭 → 캡션 p가 보일 때까지 대기 → instant scroll → 캡션 입력으로 복구한다. `addCaption`에는 번호가 포함된 문구를 전달하고 실제 p 텍스트의 일치까지 기다린다.
   - 2026-11-11 다른 레이아웃에서 `addCaption`이 캡션 대신 다음 본문에 붙여넣고 일치 대기에서 실패했다. 본문에 삽입된 문장만 제거하고 이미지를 보이는 영역에서 다시 클릭한 후, 현재 캡션 p의 좌표를 재측정해 클릭·입력하자 캡션에 들어갔다. 입력 후 캡션 p와 본문 양쪽을 확인한다. 이 사례는 helper 자체의 수정 완료를 뜻하지 않는다.
10. 이미지별 완료를 즉시 체크포인트에 저장한다. 실패한 mutation 스크립트 전체를 다시 실행하지 않는다. 제목/서식/이미지를 중복 입력하지 않는다.
11. 대표 이미지로 선택한 사진을 스마트에디터에서 클릭하고 이미지 왼쪽 상단에 표시되는 **대표 이미지 지정** 컨트롤과 현재 상태를 관찰한다. 이미 원하는 사진이 대표로 지정된 경우 그대로 두고, 아니면 컨트롤을 선택한다. 지정 상태가 그 사진에 표시되는지와 다른 사진이 대표로 남지 않았는지 확인하고 선택 파일·순번·실제 확인 결과를 체크포인트에 기록한다. 화면 구조와 selector는 실행 때 다시 확인한다. 컨트롤이나 지정 상태를 확인하지 못하면 성공으로 간주하지 말고 해당 글의 편집 상태와 재개 지점을 보존한다.

## 5. URL을 썸네일 카드로 바꾸기

1. CTA 표 직후의 빈 본문 문단에 **plain URL 네이티브 붙여넣기** 후 Enter를 누른다. HTML `<a>`만 붙인 상태로 끝내지 않는다.
2. 이번 실행에서는 SDK의 `keyboard.paste(URL)`가 네이티브 붙여넣기를 수행하여 주소창 왕복 없이 카드가 생성됐다. 사용자가 설명한 주소창 붙여넣기·다시 복사 경로의 목적은 **URL을 다시 plain clipboard 입력해 링크 인식을 발생시키는 것**이다. 이번 실행에서 주소창 자체 왕복을 했다고 기록하지 않는다. 이 기본 경로가 실패할 때만 사용자가 요청한 주소창 복사/원래 문단 재붙여넣기를 검토하되 페이지 이동·원고 유실을 피한다.
3. `.se-oglink` 생성뿐 아니라 썸네일 이미지 로딩까지 기다린다. 최초 카드에서 이미지가 누락됐으나 두 번째 카드에서 같은 URL의 이미지가 확인되어 첫 카드만 삭제·재삽입하여 해결했다.
4. 카드가 완성된 후 URL 문장 p를 클릭 → Home → Shift+End → Backspace로 URL 텍스트만 지운다. 빈 문단 개수를 관찰하고 필요한 Backspace만 추가하여 빈 text 컴포넌트를 제거한다. 무작정 Backspace를 반복해 표나 카드를 삭제하지 않는다.
5. DOM 순서가 `CTA .se-table → .se-oglink`인지 확인한다. 중간에 빈 text 컴포넌트가 없어야 한다. 네이버 자체 컴포넌트 기본 여백은 남을 수 있으며 빈 줄과 구분한다.
6. 첫 카드 재삽입이 필요하면 해당 카드만 선택 후 Delete한다. 다음 제목 앞에 빈 문단을 만든 뒤 URL을 붙여넣고 썸네일 로딩 후 URL 문단을 제거한다. 원본 링크 카드와 본문 이미지 전체를 재작성하지 않는다.
7. 공개 페이지에서 각 카드의 이미지·정보 anchor href가 2.2절에서 확정한 삽입 URL인지 확인한다. 실제 썸네일을 제공하지 않는 URL은 임의 이미지로 성공 처리하지 않고 한계를 보고한다.

## 6. 저장·공개·예약

### 발행 전 통합 검수

- 제목, 원고 주요 절·FAQ, 채택 이미지 수/순서/로드/번호가 붙은 캡션, 대표 이미지 지정 상태, 표와 번호 중복을 확인한다.
- 이미지 배치 지시와 NAVERIMG/NAVEROG marker가 0개인지 확인한다.
- 오픈그래프 개수와 썸네일, CTA 직후 배치, raw URL 문장 0개를 확인한다.
- CTA의 **td 계산 배경색**과 실제 텍스트 노드 부모의 색·크기·굵기를 측정한다. span 자체가 400이어도 안쪽 b가 700이면 굵은 글자다. 일반 본문은 변환기에서 보통체였던 문장을 전부 대조하여 누락/전체 굵기 0건이어야 한다. H2 다음, 이미지 다음, 표 다음 문장을 반드시 포함한다.
- 캡션은 `.se-caption p` 텍스트만 실제 삽입 순서의 번호와 원래 캡션을 합친 실행용 예상 문구와 비교한다. 편집 중 떠 있는 도구막대 문구가 caption.textContent에 섞일 수 있다. 본문이 캡션으로 유입되거나 표가 누락되면 발행 전에 복구한다. 대표 이미지도 지정한 파일과 순번을 다시 확인한다.
- 새 변환 스타일 또는 오류가 있으면 해당 영역만 screenshot으로 시각 확인한다. 매 이미지의 전체 snapshot은 반복하지 않는다.
- 작성 중 저장이 필요하면 해당 글의 저장 상태만 확인한다. 임시저장 목록이나 다른 초안의 개수·상태는 발행의 선행 조건이 아니다. 실제 공개 또는 예약이 확인되기 전에는 F=`ㅇ`를 쓰지 않는다.

### 카테고리와 태그

1. 상단 발행 버튼은 설정 패널을 연다. 패널의 마지막 발행 버튼이 실제 제출이다. 둘을 혼동하지 않는다.
2. `카테고리 목록 버튼`을 열어 주제와 가장 맞는 항목을 선택한다. 없으면 첫 ‘유용정보’ 카테고리를 선택한다. 현재 사례에서는 ‘앱,PC프로그램’ 선택 시 ‘IT·컴퓨터’ 주제가 함께 적용됐다.
3. TXT에 있는 관련 태그를 입력 후 Enter로 확정한다. 공개 설정·발행 시간을 확인한다. 기존의 댓글/검색 등 설정은 요청 없이 바꾸지 않는다.
4. 패널을 닫아 수정해야 하면 Escape가 성공했다. 열린 패널의 배경 div가 상단 발행 버튼 클릭을 가로막을 수 있다.

### 공개 글 기준 발행 시각

- 예약 간격은 **네이버 ID별(배정된 ego 프로필별)로 각각 독립 계산**한다. 모든 섹션의 배정 행을 계정별로 모아 해당 계정의 최신 공개 일반 글과 그 계정에 배정된 앞선 예상·예정 시각만 기준으로 삼는다. 다른 계정의 글이나 시간은 이 계정의 기준이나 대기 조건이 아니며 서로 다른 계정에는 같은 시각을 배정할 수 있다. 예를 들어 A 계정이 03:00·05:00이면 B 계정도 자신의 기준에 따라 03:00·05:00을 사용할 수 있다. 재계산할 때도 변경할 미제출 슬롯의 계정별 순서를 유지하고 다른 계정의 시각은 건드리지 않는다.
- **첫 배정 글도 자동으로 현재 발행하지 않는다.** 작성 전에 블로그 전체 글 목록의 최신 일반 글 작성일을 확인한다. 상단 공지글은 최신 글로 오인하지 않는다. `27분 전`, `4시간 전`, `19시간 전` 등은 관찰한 KST 시각과 함께 보존한다. 같은 글의 검증된 정확한 발행 시각이 있으면 이를 사용한다. 상대 시각만 있으면 표시 단위의 오차를 감안해 늦은 쪽 시각을 기준으로 계산한다.
- 기존 예약 발행 건수나 목록은 조회하지 않고, 그 확인 여부 때문에 제출을 보류하지 않는다. 이를 예약이 없다는 사실로 기록하지 않는다.
- 계정별 최신 **공개된 일반 글**을 한 번 확인하고, 그 계정의 첫 배정 글은 현재가 최신 공개 글+2시간 이상이면 즉시 발행, 아니면 최신 공개 글+2시간을 UI 분 간격으로 올림해 예약한다. 같은 계정의 두 번째 글은 첫 글의 **예상 또는 예정 시각 +2시간**, 세 번째는 두 번째 예정 시각 +2시간으로 배정한다. 첫 글이 즉시면 계획 수립 시각을 예상 시각으로 사용한다. 예: 첫 글 즉시 → 둘째 약 2시간 후, 첫 글 약 2시간 후 예약 → 둘째 약 4시간 후 예약. **24시간은 상대 날짜 표시를 확인할 구간이지 발행 간격이 아니다.** 기존 예약 목록은 보지 않으므로 이번 실행 이전 예약과는 겹칠 수 있다.
- 조정자는 전체 배정표의 계정별 `indexOnProfile` 순서로 모든 행의 시각을 **제출 전에 한 번 계산해 파일로 저장하고 배포**한다. 순번은 시각 배정용이며 먼저 제출하거나 실제로 발행될 때까지 기다리라는 뜻이 아니다. `tools/naver_workflow.py schedule-plan`으로 시각표를 생성한다. 입력의 `lastPublishedByAccount`에는 각 계정의 확인된 최신 공개 시각을 넣으며, `null`은 확인 결과 공개 글이 없는 경우에만 사용한다. 기존 `schedule_decision`은 예약 목록 확인을 요구하는 이전 방식이므로 사용하지 않는다. 이미 완료된 글은 미발행 대상에서 제외하고 그 실행의 계정별 순번을 연속으로 확정한다.
- 시각표의 `plannedPublicationTime`은 **예정치**이고 `slotIsConfirmed: false`는 미제출을 뜻한다. 작업자는 같은 계정 다른 행의 상태를 기다리지 않고 자기 배정 시각으로 독립 제출·확인한다. 첫 즉시 발행이 계획 수립보다 늦으면 실제 간격은 약 2시간에서 달라질 수 있으므로 관찰된 시각과 차이를 기록한다. 지연으로 예약 예정 시각이 이미 지났으면 과거 시각으로 제출하지 말고, 이미 제출한 글의 시각을 임의로 바꾸지 않은 채 남은 미제출 슬롯을 조정·공유하고 차이를 보고한다. 사용자가 **모든 글의 즉시 발행** 등 다른 간격을 명시하면 그 지시를 우선한다.
- `tools/naver_workflow.py next-time '2026-11-10T23:32:12+09:00' --minute-step 10` → `2026-11-11T01:40:00+09:00`. UI가 지원하는 분 간격으로 위로 올림하며 자정·월말·연말을 처리한다. 실제 분 옵션은 현재 UI에서 확인한다.
- `예약` 라디오 input ref는 label에 가려질 수 있다. 실제 ‘예약’ label을 클릭하고 나타난 날짜 textbox와 시/분 select의 현재 값·옵션을 읽어 설정한다. 입력 후 세 값을 다시 확인하고 제출한다.
- 시트/호스트 시간대가 America/Los_Angeles여도 예약은 사용자 요청의 Asia/Seoul 기준이다. 시트 전체 시간대를 바꾸지 않는다.
- 작업 지연으로 계산한 예약 시각이 지났으면 과거 시각을 입력하지 않는다. 위의 미제출 슬롯 조정 원칙에 따라 현재 시각과 이미 제출된 결과를 반영한다.
- 예약 제출 후 해당 글의 확인 화면에서 제목·계정·예약시각이 확정된 경우에만 예약 완료로 기록한다. 현재 작성창에 예약값만 입력한 것은 성공이 아니다. 확인 화면을 확보하지 못하면 결과 불확실로 기록한다.
- **검증 범위:** 2026-11-11 chocolateelf 최근 글 11월 3일·예약 0건 → 현재 발행, qta14 최근 글 11월 10일 23:32·예약 0건 → 11월 11일 01:40 예약을 실제 제출했다. 이후 ‘예약 발행 1건’ 클릭 → 제목과 `2026.11.11 01:40` 확인 → 글을 다시 열어 저장된 서식까지 검증했다. 기존 예약이 있는 상태에서 새 글을 추가 제출하는 경우는 아직 실측하지 않았으며 시간 계산 회귀 테스트로 검증했다.

## 7. 공개 확인과 두 시트 기록

공개 페이지에서 실제 제목·이미지·번호가 붙은 설명·카드 href·썸네일과 **CTA 색상/굵기, 일반 본문 보통체**를 확인한다. 대표 이미지도 저장된 예약 글이나 공개 결과에서 확인 가능한 표시를 확인하고, 보이지 않는 상태는 추측하지 말고 검수 한계를 기록한다. 예약은 해당 글의 확인 화면이나 직접 열 수 있는 저장된 글에서 서식을 검수하고, 접근할 수 없으면 미검수로 기록한다. 공개되지 않은 예약 글을 공개 검수 완료라고 쓰지 않는다. `meta[property="og:url"]`에서 실제 깨끗한 공개 URL을 얻는다. `canonical`이 없다고 URL을 추측하지 않는다. 발행 완료 관찰 시각은 실제 서버 초 단위와 구별하여 `publicationTimeSource: observed_completion`으로 기록한다.

현황 시트: `1YVfd6VIEEZCbAjNw-n3Cre6UrcrIIo28XQlZd1Sv3yI`, 탭 `네이버블로그 현황`.

1. 성공 결과를 먼저 `웹조사/evidence/naver-state.json`에 저장한다.
2. 쓰기 직전 콘텐츠표 실제 키워드/F와 현황 E열 마지막 데이터·쓰기 대상 CellData를 다시 읽는다. 공백·0·FALSE·수식 결과 공란은 빈 셀이 아니다.
3. 현황 E열 마지막 데이터 다음 행에 아래 셀만 쓴다. 중간의 빈 행을 채우거나 표 전체를 append/덮어쓰지 않는다.

| 열 | 값 |
|---|---|
| A | 공개 발행일 또는 예약 예정일, KST 기준 날짜값, `yyyy-mm-dd` 표시 |
| D | 키워드의 콘텐츠표 탭 이름 |
| E | 메인 키워드 |
| F | 본문에 삽입한 애드센스 URL |
| H | 실제 네이버 공개 URL / 예약이면 `2026년 11월 11일 01시 40분 예약발행` |
| 해당 I/J/K/L 하나 | 배정 계정에 `홍보성` |

4. A/D/E/F/H/해당 계정 열을 하나의 batchUpdate로 기록한다. A에는 숫자형 날짜 일련값을 쓰고 기존 날짜 표시를 유지한다. 날짜 형식이 없으면 A 대상 셀만 `DATE/yyyy-mm-dd`로 설정한다.
5. 콘텐츠표 해당 행 F에 한글 자음 `ㅇ`를 쓴다. E/G/H/L이나 다른 계정 열은 변경하지 않는다.
6. 두 파일은 원자적 트랜잭션이 아니다. 현황 기록 → 콘텐츠표 F → 두 범위 재조회 순으로 진행하고 부분 성공은 로컬에 각각 저장한다.
7. 현황 C열의 ARRAYFORMULA·B/G·다른 계정 값·서식·유효성을 보존한다. 기존 빈 행에 서식이 있으면 행 복사 없이 해당 셀 값만 쓴다.
8. 재조회 값과 날짜 표시를 확인한다. Google 화면 접근이 가능하면 대상 범위만 확인한다. 의도적으로 CLIP인 기존 긴 URL 열을 넓히지 않는다.

| 상태 파일·실패 기록·알림 | 종료 또는 사용자 제어 경계 처리 |

### 재사용 도구

```powershell
# request.json: {"jobs":[{"tab":"앱사용","row":34,"keyword":"...","promotionUrl":"...","folder":"YY_MMDD/탭_키워드"}]}
python3.14-64.exe tools/naver_workflow.py plan request.json .session/naver-run/assignments.json
# 시각 입력: {"jobs":[배정표의 jobs],"now":"2026-11-11T00:30:00+09:00","lastPublishedByAccount":{"계정":"확인한 ISO 시각 또는 null"},"minuteStep":10}
python3.14-64.exe tools/naver_workflow.py schedule-plan schedule-input.json .session/naver-run/schedule.json
python3.14-64.exe tools/naver_workflow.py prepare 'YY_MMDD/탭_키워드' .session/naver-run/prepared.json
python3.14-64.exe tools/naver_workflow.py next-time '2026-11-10T20:00:00+09:00' --minute-step 10
python3.14-64.exe -m unittest discover -s tools -p test_naver_workflow.py -v
node tools/test_naver_editor.mjs
```

`plan/schedule-plan/prepare/sheet-plan`은 기존 출력 파일을 덮어쓰지 않는다. 이미 파일이 있으면 읽어 재개한다. 시각표 생성은 계획만 저장하며 실제 발행·예약이 아니다. `sheet-plan`은 요청 **계획만 생성**하며 실제 시트 쓰기는 연결 도구로 한다. 입력 계약 예제는 `tools/test_naver_workflow.py`의 fixture를 참고한다. 신규 행 검증용이며 기존 현황 행 복구는 live 값을 읽고 필요한 빈 셀만 별도 계획한다. 유효성 규칙이 있으면 도구가 거절하므로 실제 허용값을 확인한다.

브라우저 `.mjs`는 이번 실행에서 작성한 새로운 라운드 파일만 실행한다. 재사용 helper는 live selector 구조를 먼저 확인하고 import한다. Windows는 UTF-8 파일 + ASCII `file:///.../round-N.mjs` 진입점을 쓴다. PowerShell `Get-Content | ego-browser`와 다중행 `-e`는 피한다.

상태/개수/불일치만 출력하고 전체 HTML·시트·광고 iframe snapshot을 반복하지 않는다. metadata와 같은 시점의 헤더는 재사용하되 발행 전·시트 쓰기 전 live 확인은 유지한다. 이미지 업로드·키보드 입력은 같은 글에서 순차 루프로 묶고, 다음 행동을 바꾸는 분기에서만 새 snapshot을 읽는다. 캡처/CDP 뒤에는 ref를 새로 얻는다. 토큰 절감률은 측정 전 수치로 단정하지 않는다.

### 서식 자동 검수

`auditStyles(page, data.normalParagraphs)`로 계산 스타일과 콘텐츠를 읽고 `assertStyleAudit(audit, plan, {publicPage, expectedTables})`가 통과해야 제출/완료 처리한다. 여기의 `plan`은 이미지 캡션에 실제 게시 순번을 반영한 실행용 계획이어야 한다. 기존 helper는 원본에서 추출한 캡션을 그대로 비교하므로 번호를 자동으로 더한다고 가정하지 않는다. CTA 색상·크기·굵기, 보통체 문장 누락/불필요한 볼드, 이미지 수·로드·번호 포함 캡션, 카드 수·썸네일·CTA 인접, raw URL/표식 잔존, 표 수를 검사한다. 대표 이미지 선택 상태는 이 helper의 기존 검수에 포함돼 있다고 가정하지 말고 별도로 확인한다. 공개 페이지에서는 카드 href도 검사한다. 예약 편집창에서 href가 없다는 이유로 공개 검수로 대체하지 않는다.

## 9. 오류·사용자 제어·완료

- 오류마다 마지막 성공 단계, 실패 동작, 실제 오류, 현재 저장/발행 상태, 시도한 대안, 다음 단계, Space/계정/공개 URL을 기록한다. 이미 성공한 입력·업로드·게시를 재실행하지 않는다.
- `작성 중인 글이 있습니다` 안내에서는 **확인**을 선택하고 복구된 제목과 내용을 살펴본다. 진행 대상과 일치하면 체크포인트를 대조해 이어간다. 다른 글이면 그 내용을 보존하고 임시저장 또는 예약 목록에서 진행 대상의 제목을 찾아 선택한다. 선택할 때 현재 글을 임시저장하고 불러올지 묻는 확인창이 나타나면 저장 후 불러오기를 선택한다. 대상 제목이 없는 신규 작업은 복구한 다른 글을 저장한 뒤 편집기 `더보기 → 새 글쓰기`에서 빈 편집기를 확인하고 작성한다. 사용자가 명시한 이 복구 방식은 다른 글을 덮어쓰거나 삭제하라는 뜻이 아니다.
- 같은 Space가 블로그 설정 등 작업과 무관한 화면에 있으면 현재 내용을 보존한 뒤 해당 계정의 `https://blog.naver.com/{네이버ID}/`로 돌아가 글쓰기를 열고 같은 절차를 적용한다. 이미 제출한 글은 임시저장 목록에 제목이 없더라도 먼저 동일 글의 공개·예약 결과를 확인하고, 결과가 불확실한 상태에서는 새 글을 제출하지 않는다. 실제 관찰과 복구 경로는 [NAVER_UPLOAD_20261113.md](archive/NAVER_UPLOAD_20261113.md)에 기록한다.
- 사용자 제어로 전환됐다는 SDK 오류가 나오면 해당 Space에서 모든 조작을 멈춘다. 사용자가 ‘계속’이라고 명시한 뒤에만 같은 ID로 `takeOverTaskSpace`한다. 그 행을 다른 도구/Space로 옮겨 우회하지 않는다. 별개 행은 자기 Space에서 독립적으로 진행하며, 이때 사용자 제어 중인 행에는 접근하지 않는다. 브라우저 또는 런타임 전체가 제어 불가라고 알리면 해당 제약을 우회하지 않는다.
- ego-browser 화면 캡처가 필요하면 현재 TaskSpace의 Page에서 `tools/research_browser.mjs`의 `capture()`를 우선 사용한다. 최소화된 같은 창은 함수가 자동으로 복원한다. 직접 CDP 복원은 `capture()`를 사용할 수 없을 때만 [웹자료수집.md 7절](웹자료수집.md#ego-taskspace-창-복원과-google-검색-결과-캡처-2026-11-12)에 따른다. 타임아웃이면 현재 내용과 저장 상태를 먼저 보존하고, 정상 제어 상태인 같은 Space에서 재확인한다.
- 각 키워드가 성공하고 해당 상태·시트 재조회·문서 기록이 끝나면 그 키워드의 Space에서 `task.finish({keep:[]})`를 정확히 한 번 수행한다. 오류·사용자 제어 대기 중인 Space는 finish하지 않는다. 다른 키워드의 Space나 사용자 소유 탭을 종료하지 않는다.
- 팝업 조회형은 팝업 전체 행·탭 수, 섹션별 배정·보류 건수, 실제 채팅·Space 수와 동시 실행 제약을 보고한다. 행별로 탭·실제 행·키워드, 로컬 원고 경로, 계정과 공개/예약 결과·KST 시각·실제 공개 URL, 두 시트 재조회 결과, 보류·실패 사유와 재개 지점을 남긴다.
- 최종 완료/중단 시 `python3.14-64.exe tools/naver_workflow.py notify complete` 또는 `notify paused`로 Windows 알림을 표시한다. 알림 실패는 실제 게시 성공과 분리해서 기록한다.
